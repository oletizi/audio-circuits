This is the entry point to the h7-platform documents. It says what the platform is, lists the documents, maps every platform file of the pedals repository at commit `5b926d0` to where its content now lives or to why it stayed behind, explains how to read the pedals citations inside the two JSON records, records the licences, and warns where those records still state values that are no longer in force. ## What the platform is

h7-platform is a reusable STM32H7 digital pedal platform: stereo 24-bit, 48 kHz audio through a PCM3060 codec, USB with MIDI over USB, an expression input, six configurable control positions, two footswitches and two LEDs, in a Hammond 1590BB. Each pedal built on it is meant to differ only in its firmware and its enclosure art. The owner split the original one-board design into a socketed processor module (**h7-module**) on the Daisy Seed 40-pin pinout and an audio pedal board (**h7-pedal**) that it plugs into, plus a minimal **bring-up carrier** for a new module's first power. During development a real Daisy Seed stands in for the module. [architecture.md](architecture.md) describes the three boards, the 40-pin interface between them and the rules it is held to.

Nothing here has been built, modelled or drawn. These documents carry the design knowledge from the pedals repository, where the split's first stage (S1, the module contract and its analyses) was finished and the second (S2, splitting the schematic) never started. The contract is still a draft. Every figure in these documents is paper analysis of a board that has not been built. Phase 2 models the circuits in this repository, phase 3 draws them, and phase 4 lays out the boards for PCBWay ([port spec](../superpowers/specs/2026-11-10-digital-pedal-platform-port-design.md), *The phases*).

## Documents

In this directory:
- [decisions.md](decisions.md): the owner decisions, the facts the owner supplied, and the controller rulings, each labelled by the authority its source gives it, with how an amendment resolves.
- [architecture.md](architecture.md): the three boards, the 40-pin interface, the power domains, and what is known about the Daisy Seed.
- [power.md](power.md): the power entry, VIN_MOD, 3V3_D, the pedal digital rail and the power-fail circuit.
- [analog.md](analog.md): the analog stages, VREF_A, the codec domain and SAI timing.
- [bypass-relay.md](bypass-relay.md): the bypass relays and the power-fail path to bypass.
- [processor-and-memory.md](processor-and-memory.md): the module's MCU, SDRAM, flash and clocks.
- [firmware-facing-requirements.md](firmware-facing-requirements.md): the hardware constraints firmware imposes or depends on. This repository does not own firmware.
- [mechanical-and-controls.md](mechanical-and-controls.md): the enclosure, the stack height, the module envelope and the control positions.
- [layout-B.svg](layout-B.svg): the record of layout B, the layout the owner chose ([O-18](decisions.md#o-18)). It is a regeneration of pedals' `candidate-B.svg` (pedals `b0e69c8`) with the control, footswitch, LED, jack and relay positions unchanged; [mechanical-and-controls.md](mechanical-and-controls.md) §4.3 lists what the regenerations changed. It is a record, not something to regenerate.
- [parts.md](parts.md): the parts already chosen, with MPN, LCSC code where one was chosen, and the source of each choice.
- [layout-carry-forward.md](layout-carry-forward.md): what layout must honour, restated against the split boards.
- [schematic-checklist.md](schematic-checklist.md): the checklist items that are about the circuit.
- [bring-up.md](bring-up.md): the bring-up acceptance checklist, BU-01 to BU-29 and BL-1 to BL-4.
- [open-items.md](open-items.md): every unresolved requirement, allowance and freeze blocker, each with the phase that must close it, and the conflict entries.
- [research/proven-reference-designs.md](research/proven-reference-designs.md) and [research/processor-module-form-factors.md](research/processor-module-form-factors.md): the two platform research surveys.

## Licences

Two licence files crossed unchanged to [circuits/h7-platform/](../../circuits/h7-platform/). They were read in full at the pin before this section was written.

- [LICENSE-OSCAR](../../circuits/h7-platform/LICENSE-OSCAR) covers the **core MCU, SDRAM and flash circuitry**, derived from DADDesign-Projects **OSCAR_PROC_01** at commit `012f013d36ca110554ac18d96e6703bb5525aea5`, under the MIT licence (Copyright (c) 2025 DADDesign-Projects), which the file reproduces. It also covers the **codec (PCM3060) circuitry**, derived from **OSCAR_AUDIO_01** at commit `6a6d1b3e655bee5573527dd4ebe8828bc2561f0d`, whose `LICENSE` file is the same MIT text.
- The OSCAR_AUDIO_01 licence statement is unresolved upstream: its `LICENSE` file is MIT, but its README says "This project is licensed under the Apache License 2.0". `LICENSE-OSCAR` records Apache-2.0 alongside MIT for the codec circuitry "until the author confirms which license governs", with the work, commit, copyright, the absence of a NOTICE file, and a statement of changes under Apache-2.0 section 4(b).
- [LICENSE-APACHE-2.0](../../circuits/h7-platform/LICENSE-APACHE-2.0) is the full text of the Apache License, Version 2.0, which that attribution points to.

`LICENSE-OSCAR` names `h7-platform/boards/v1` as where the derived circuitry is, and its statement of changes describes the v1 codec sheet (U3, J5): that is what v1 contained, which is all it is. The obligation follows the circuitry, not the v1 files: into the phase-2 models and the phase-4 fabrication files of h7-module (OSCAR_PROC_01) and h7-pedal (OSCAR_AUDIO_01). The open question is the open item OSCAR-AUDIO-LICENCE-L1 in [open-items.md](open-items.md), `CORE-BRIEF.md`'s licence item L1: ask the author and record the answer in `LICENSE-OSCAR`. Until then nothing here treats it as settled.

ST's pin data in the pedals `vendor/st-pin-data/` is BSD-3-Clause; it did not cross, so it carries no obligation here.
