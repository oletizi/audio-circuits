  for `"none"`.
- New `generatedNote(schematic)`: for `"generated"` only, one `<p
  class="note">` line saying the sheet was generated by `schgen` from the
  board's own authoring declaration and is not hand-drawn, printed right
  after the header. Empty for every other kind.
- `noSchematicNotice` now gates on `schematic.kind !== "none"` (was `!==
  "printed"`), so it fires only for `"none"` and never for `"withheld"` or
  `"generated"`.
- New `withheldSchematicNotice(boardName, schematic)`: the bordered notice
  for `"withheld"`, naming the board, the declaration path, the circuit the

  `noSchematicNotice`, `withheldSchematicNotice`, then the images - so at
  most one of the three notice-producing calls is ever non-empty for a given
  input.

### `tools/guide/packet.ts`

- New `resolveSchematic(declaration, schPath, repoRoot, name, boardRefsFn,
  boardSheetsFn)`: the packet's second schematic source. When `schPath` is
  defined, returns `{ kind: "printed", ... }` unchanged. When it is
  undefined, resolves `name = boardName(declaration)`, looks up the board's
  `BoardRef` via `boardRefsFn(repoRoot).find((r) => r.name === name)`, and
  if found, calls `boardSheetsFn(ref, repoRoot, { outDir: <mkdtempSync temp
  dir>, pdf: false })`. From the result:
  - no `BoardRef`, or `outcome === "no-declaration"` -> `{ kind: "none",
    ... }` (today's behaviour, unchanged).
  - `outcome === "refused"` -> `{ kind: "withheld", reason: <blocker in
    full> }`.
  - `outcome === "generated"` and `!drawings.every((d) =>
    d.fieldFallbacks.length === 0)` -> `{ kind: "withheld", reason: "<n>
    fallback field placement(s): text the placer could not keep clear" }`,
    where `<n>` is `result.fallbacks.length` (the flattened count
    `boardSheets` already carries - equal by construction to summing
    `fieldFallbacks.length` across `drawings`).
  - `outcome === "generated"` with every sheet clean -> `{ kind:
    "generated", path: SCHEMATIC_PDF }`, carrying `schematicRoot` (the
    absolute `.kicad_sch` path) back to the caller.
  - Returns the `tempDir` it created (or `undefined` when none was needed)
    so the caller can clean it up once it is actually done with it.
- In `writeGuidePacket`: the rest of the function (building `html`, staging,
  writing files, the return-value report) now runs inside a `try { ... }
  finally { fs.rmSync(resolution.tempDir, ...) }` so the temp directory
  outlives the PDF export of a clean generation and is removed on every
  exit, success or throw.
- In the staging `try` block: when `schematic.kind === "generated"`, calls
  `defaultExportSchematicPdf(deps.kicadCli, schematicRoot,
  path.join(staging, SCHEMATIC_PDF))` (the brief's literal instruction - via
  `defaultExportSchematicPdf` directly, not through the `deps.exportSchematicPdf`
  override, since a generated sheet's root never comes from a declaration a
  caller would want to redirect).
- `packetFiles` is now called with `hasSchematic = schematic.kind ===
  "printed" || schematic.kind === "generated"`, per the brief.
- The console report's trailing line is now keyed off `schematic.kind`
  rather than `schPath === undefined`: `"none"` keeps the old sentence
  verbatim, `"withheld"` gets a new sentence naming the reason, and
  `"generated"`/`"printed"` add nothing (matching the page, which also adds
  nothing extra for those two beyond the one-line generated note).

## Deviation from the brief, and why

**I added two new optional fields to `GuideDeps`: `boardRefs` and
`boardSheets`**, defaulting to the real `tools/schgen/board-sheets.ts`
functions (imported as `schgenBoardRefs`/`schgenBoardSheets` to avoid name
collision), and threaded them into `resolveSchematic` as explicit function
parameters rather than calling the imports directly.

The brief's pseudocode calls `boardRefs(repoRoot)` and `boardSheets(...)`
directly. I did not do that unmodified, because `boardRefs` does a real
`fs.readdirSync(path.join(repoRoot, "boards"))` against the real filesystem,
with no injection seam of its own. `tools/guide/packet.ts` otherwise injects
every real side effect through `GuideDeps` (`runVeroroute`,
`exportSchematicPdf`, `printGuidePdf`, `loadCircuit`) specifically so a unit
test can run against a synthetic `repoRoot` like `/repo` through an in-memory
`GuideFs`, never touching real disk. `tests/guide/packet.test.ts`'s existing
test `"a board that declares no schematic gets a five-file packet that
prints why"` does exactly that - `DECLARATION.dir = "/repo/boards/test-board"`,
`deps.repoRoot = "/repo"`, no real `/repo` directory exists. Calling the real
`boardRefs("/repo")` there throws `ENOENT: no such file or directory, scandir
'/repo/boards'` - not a refusal with a reason, just an unhandled crash from a
function the test never asked to exercise.

I fixed this by making `boardRefs`/`boardSheets` overridable exactly the way
every other real-world dependency in this file already is, and adding one
line (`boardRefs: () => []`) to the shared test harness, with a comment
saying why: that harness's fake `/repo` is never a real repository, so for
every test that drops `schPath` the census correctly finds nothing, which is
the same "none" outcome the test expected before this task. This is
consistent with the project's architecture guidance (constructor/dependency
injection, composition over inheritance) and is, I believe, what the
pseudocode's authors would have written had they been looking at this
specific test file rather than describing the production code path. I did
not touch `tests/guide/clusters-packet.test.ts` (uses the real
`moduleRepoRoot()` as `repoRoot`, so the real `boardRefs`/`boardSheets`
default works there unmodified and genuinely exercises `pultec-low-boost`'s
withheld outcome - see below) or `tests/cli/perfboard-guide-verb.test.ts`
(uses a real throwaway temp directory tree as `repoRoot`, so the real
functions also work there unmodified).

I flag this as the one place I diverged from the brief's literal text,
because it is new public surface on `GuideDeps` the brief did not ask for.
I judged it necessary rather than optional: without it, the full suite does
not reach 0 fail.

# Fix round 1/5 - five review items

Commit: `65055b063296bf216e11a11fcd4a16368cac6af3` on `feature/schematics-tooling`

The review verdicted SPEC and quality both passing and traced the four
outcomes, the gate predicate, the temp-dir containment and the injected
defaults as correct. Five items remained; all five are addressed below.

## Item 1 (Important) - the generated branch now uses the injected export

`tools/guide/packet.ts`'s `"generated"` branch called `defaultExportSchematicPdf`
directly, bypassing `deps.exportSchematicPdf`. The brief told me to do exactly
that; the coordinator flagged it as the brief's own defect, not mine, because
it defeats an injection seam the file already has everywhere else.

Fixed: that call site now reads `(deps.exportSchematicPdf ??
defaultExportSchematicPdf)(deps.kicadCli, schematicRoot, path.join(staging,
SCHEMATIC_PDF))` - the same pattern the `schPath !== undefined` branch beside
it already uses. A comment at the call site records why: `tests/guide/clusters-packet.test.ts`
injects a THROWING `exportSchematicPdf` specifically so a stray export is
loud, and runs the real `pultec-low-boost` board through the real `repoRoot`.
Today that board resolves `"withheld"` so the throw is never reached; the day
its fallback count drops to zero it resolves `"generated"`, and without this
fix that line would have called the REAL export function directly, spawning
the real `kicad-cli` at that test's fake `/fake/kicad-cli` path instead of
tripping the test's own guard - a trap that arms itself exactly when the
arrangement work succeeds.

## Item 2 (Important) - the temp directory no longer leaks on a throw from `resolveSchematic` itself

Before this fix, `mkdtempSync` ran inside `resolveSchematic`, and the only
cleanup (`fs.rmSync(resolution.tempDir, ...)`) lived in the CALLER's
`finally`, which only runs once `resolveSchematic` has already returned. Two
throw paths sat between the two: the `schematicRoot === undefined` refusal,
and - the real one - anything `boardSheetsFn` throws straight through, since
`boardSheets()` in `tools/schgen/board-sheets.ts` wraps only `generate()` in
its own try, so `kicadVersion()`, `stockSymbolDir()` and `parityDesign()`
throw past it uncaught.

Fixed inside `resolveSchematic` itself (now in the new
`tools/guide/schematic-source.ts` - see item 3): the body from
`fs.mkdtempSync` onward is wrapped in its own `try { ... } catch (caught) {
fs.rmSync(tempDir, ...); throw caught }`. A normal return (any of the four
outcomes) still hands `tempDir` back in the `SchematicResolution` for the
caller to remove once it is actually done with it - ownership only transfers
on success. A throw is caught, the directory is removed, and the original
error is rethrown unchanged.

## Item 3 (Important) - `resolveSchematic` moved to `tools/guide/schematic-source.ts`

`tools/guide/packet.ts` was 499 lines, one edit away from breaking this
project's 300-500 line ceiling. `resolveSchematic`, its `SchematicResolution`
interface, its doc comment, and the `SCHEMATIC_PDF` constant it needs all
moved to a new `tools/guide/schematic-source.ts` (187 lines).

`SCHEMATIC_PDF` now has one authoritative definition, in the new file;
`packet.ts` imports it for its own internal use (`import { ...,
SCHEMATIC_PDF } from "./schematic-source.ts"`) and re-exports it (`export {
SCHEMATIC_PDF } from "./schematic-source.ts"`) so every external consumer's
`import { SCHEMATIC_PDF } from ".../packet.ts"` keeps working unchanged - I
checked with a repo-wide grep that nothing outside `packet.ts` imported it
directly before this change, and confirmed afterward that the public import
path is unchanged. `packet.ts`'s own exported surface (`GuideFs`, `GuideDeps`,
`SCHEMATIC_PDF`, `CLUSTERS_SVG`, `GUIDE_HTML`, `GUIDE_PDF`, `packetFiles`,
`defaultExportSchematicPdf`, `writeGuidePacket`) is otherwise unchanged; no
file outside `tools/guide/packet.ts` and `tools/guide/schematic-source.ts`
needed an import changed, and `bun run typecheck` across the whole repo
confirms it.

`node:os` and the `GuideSchematic` type import became unused in `packet.ts`
once `resolveSchematic` moved out, and were removed.

## Item 4 (Important, PARKED - recorded, not fixed)

A comment on `resolveSchematic` in the new `tools/guide/schematic-source.ts`
(just above the function, the paragraph beginning "PARKED") now records: that
`deps.kicadCli`/`--kicad-cli` governs only the PDF-export steps, never the
generation `boardSheetsFn` performs; that the generation resolves its own
`kicad-cli` independently, through `tools/schgen/kicad-run.ts` reading

defaultKicadCli()`, resolved once at module load, never from a flag or a
`GuideDeps` field); what can go wrong (a board that used to generate starts
refusing here for an operator whose working `kicad-cli` is only at the
`make`-resolved path); and what to check (whether `KICAD_CLI` the environment
variable, or schgen's own default absent that, points at the same binary
`--kicad-cli` does). I did not touch `boardSheets()`, `kicad-run.ts`, or any
other schgen file - threading one resolution through to the other is schgen's
own territory, per the coordinator's instruction, and I left it parked rather
than attempting a fix. `docs/known-gaps.md` was not touched (frozen); the
comment is the record, at the code it concerns.

## Item 5 (Minor, promoted - fixed)

`resolveSchematic`'s gate used to be `result.drawings.every((d) =>
d.fieldFallbacks.length === 0)` alone, which is vacuously `true` on an empty
`drawings` array - an outcome of `"generated"` with zero sheets drawn would
have passed the gate having examined no placed text at all. The reviewer
could not construct that state from the real `generate()`, so it was latent
rather than reachable, but it is this project's cardinal failure shape (a
check reporting a pass on no evidence) and the fix is one added condition.

Fixed: before the fallback check, `resolveSchematic` now tests
`result.drawings.length === 0` first and withholds with a reason distinct
from the fallback-count reason - `"generated 0 sheets: NOT MEASURED - no
sheet was drawn, so there is no placed text to confirm clear, and that is not
the same claim as a clean generation"` - wording deliberately echoing
`tools/schgen/board-sheets.ts`'s own `renderBoardSheets`, which makes the
same distinction for its own zero (`"fallback field placements: NOT MEASURED
- no board produced a sheet, so there is no placed text to count"`). The two
refusal reasons are now distinguishable in the guide's withheld notice: "0
sheets drawn" vs. "N fallback field placement(s)" name which of the two
conditions failed.

Also per the coordinator's "while you are in there": `tests/guide/clusters-packet.test.ts`'s
module comment claimed only disk and the browser were injected. That stopped
being true the moment `resolveSchematic` started calling the real
`boardRefs`/`boardSheets` by default for a board with no `"sch"` (this test
does not override them, deliberately - see its own comment). The module
comment now has a new paragraph, "NOT ONLY DISK AND THE BROWSER ARE INJECTED
ANY MORE", explaining that this packet now runs a real `schgen` generation
for `pultec-low-boost` against the real `repoRoot`, that it resolves
`"withheld"` today (five fallback field placements), and why the throwing
`exportSchematicPdf` stub matters for the day that count reaches zero.

## Left alone, per instruction

The unreachable second refusal inside `resolveSchematic` - `outcome ===
"generated"`, every sheet clean, but `result.schematicRoot === undefined` -
is untouched. It is harmless (nothing can reach it from the real
`boardSheets()`, which always carries a `schematicRoot` on a clean
`"generated"` outcome) and was explicitly called out as deferred.
