Concerns
1. Net rename: CORE-BRIEF's USB_DM / USB_DP nets would collide with the contract's own USB_DM / USB_DP (pins 36 and 37, PB14/PB15). I named the DFU nets DFU_USB_DM and DFU_USB_DP. No pin moved. Task 6 and later must use these names.
2. ST spells some port names with decoration in the XML: "PA13 (JTMS/SWDIO)", "PA14 (JTCK/SWCLK)", "PH0-OSC_IN (PH0)", "PH1-OSC_OUT (PH1)", "PC14-OSC32_IN", "PC15-OSC32_OUT". McuPin.name keeps ST's text verbatim; portName() extracts the leading Pxn / Pxn_C, and a test asserts all 140 I/O ports resolve to unique plain names. Later tasks should look pins up with portName, not name.
3. PC2_C is a "_C" direct-analog pad in ST's data (PC3_C is in the same family, which CORE-BRIEF :359 notes needs an analog switch closed for PC3_C). I did not check what, if anything, ST requires for using PC2_C as a plain ADC input; the rule does not look at it. The controller may want to rule on whether a non-_C pin should be preferred. Not asserted from memory.
4. PA9 (VBUS sense, CORE-BRIEF :398) is excluded from MODULE_PINS: split spec 6.2 (:519) says PA9/PA10 stay unallocated and the USB socket needs no VBUS sensing (6.4). The brief lists only PA11 and PA12 for DFU.
5. NRST, BOOT0 and power pins are not in MODULE_PINS (not ports); the brief assigns the power-reach assertion to Task 6. The test asserts the data's 33 Power pins; the per-name counts (14 VDD, 12 VSS) are not yet asserted in a test and belong with Task 6's assertion.
6. Pre-existing failures I did not touch or run: make check at boards/pt2399-core; tests/stripboard/temp-scratch.test.ts.
